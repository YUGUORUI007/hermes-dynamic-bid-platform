# Hermes 动态投标项目管理平台需求文档

版本：v1.0  
日期：2026-07-21  
状态：待产品确认

## 1. 项目背景

现有系统由网站内置 AI 解析招标文件，并把结果写入一套固定项目字段。新方案取消网站内置 AI 分析：用户把招标文件或文字信息交给 Hermes，Hermes 根据材料实际内容自主组织信息，经用户在对话中明确确认后，通过 Skill 调用平台 API 创建或更新项目。

平台不再规定完整的投标业务字段。平台负责身份鉴权、数据校验、可靠存储、动态渲染、项目生命周期、审计和归档；Hermes 负责理解材料、决定内容结构、请求用户确认和调用接口。

## 2. 产品目标

1. 任意招标项目都能使用不同的信息结构，不受固定字段表单限制。
2. Hermes 未获得用户明确确认时，不得正式写入或修改项目。
3. Hermes 提交的数据能够在网站中稳定、清晰、可追溯地呈现。
4. 用户可以快速掌握项目状态、负责人、关键节点、风险和下一步行动。
5. 所有外部写操作均可鉴权、可追踪、可重放保护、可审计。
6. 保留人工维护能力，避免业务完全依赖 Hermes。

## 3. 非目标

- 网站不负责 OCR、LLM 调用、招标文件解析或提示词管理。
- 第一版不在网站内实现聊天机器人。
- 第一版不提供任意 HTML、CSS 或脚本渲染，避免内容注入风险。
- 第一版不建设复杂 BPM 审批引擎。

## 4. 核心原则

### 4.1 最小固定外壳

平台仅固定以下系统字段：

- `id`：项目唯一标识。
- `title`：项目名称。
- `status`：项目生命周期状态。
- `owner`：负责人。
- `summary`：项目摘要。
- `schema_version`：动态内容协议版本。
- `content`：Hermes 决定的动态内容。
- `created_at`、`updated_at`、`archived_at`：系统时间。

其中 `title`、`status` 用于列表、搜索、权限和归档。除系统外壳以外的业务字段均不固定。

### 4.2 动态内容模型

动态内容由有序 `sections` 组成。每个 section 包含标题、说明、展示方式和有序 blocks。支持的 block 类型包括：

- `field`：标签和值，可声明文本、日期、金额、电话、链接等语义。
- `status`：带语义色的状态项。
- `text`：多行正文。
- `list`：有序或无序列表。
- `table`：结构化表格。
- `timeline`：时间节点列表。
- `checklist`：可完成的执行事项。
- `callout`：普通、提示、警告、危险信息。
- `files`：附件引用。
- `divider`：内容分隔。

平台只渲染白名单 block，不接受 Hermes 提交原始 HTML。

### 4.3 展示提示

Hermes 可以提交受限的展示提示：

- section 顺序和 block 顺序。
- `priority`：普通、重要、紧急。
- `visibility`：详情可见、摘要可见。
- `width`：整行、半行、三分之一行。
- `collapsible`：是否可折叠。

Hermes 不得提交任意颜色、字体、CSS 或 JavaScript。最终视觉由平台设计系统统一控制。

## 5. 用户角色

- 管理员：管理用户、API Token、项目、归档和审计记录。
- 编辑者：创建、修改、归档项目，维护动态内容。
- 查看者：查看被授权项目。
- Hermes Client：仅能通过 Token 调用已授权 API，权限与 Token Scope 对应。

## 6. 关键业务流程

### 6.1 Hermes 新建项目

1. 用户向 Hermes 发送文件或文字。
2. Hermes 自主解析并组织动态内容。
3. Hermes 在对话中向用户展示拟写入摘要。
4. 用户明确确认。
5. Hermes 先调用校验接口，获得规范化预览和查重结果。
6. 若存在疑似重复项目，Hermes必须再次询问用户是新建还是更新。
7. Hermes携带确认信息和幂等键调用创建接口。
8. 平台返回项目 ID、版本号和详情地址。

### 6.2 Hermes 更新项目

1. Hermes按项目 ID、招标编号或名称搜索项目。
2. Hermes向用户说明将修改的内容。
3. 用户确认后，Hermes提交基于当前版本的 patch。
4. 平台校验版本，避免覆盖他人刚刚完成的修改。
5. 平台写入新版本并生成审计记录。

### 6.3 人工修改

网站允许编辑系统字段，并通过动态编辑器增删、排序 section 和 block。人工操作与 Hermes 操作使用同一版本和审计机制。

## 7. API 需求

基础路径：`/api/v1`

- `POST /validate/project`：校验、规范化和查重，不写数据库。
- `POST /projects`：新建项目。
- `GET /projects`：分页、筛选和搜索项目。
- `GET /projects/{id}`：读取完整动态项目。
- `PATCH /projects/{id}`：局部更新，必须提供当前版本。
- `POST /projects/{id}/status`：更新生命周期状态。
- `POST /projects/{id}/followups`：追加跟进记录。
- `POST /projects/{id}/archive`：归档项目。
- `GET /schema/project`：读取当前动态内容协议和枚举。

通用要求：

- Bearer Token 鉴权，Token 只保存哈希。
- Scope 至少包含 `projects:read`、`projects:write`、`projects:archive`。
- 所有写请求支持 `Idempotency-Key`。
- 更新请求使用版本号或 `If-Match` 防止并发覆盖。
- 统一错误格式，包含错误代码、字段路径和可执行修复建议。
- 限制请求体大小、section 数量、block 数量和单字段长度。
- 审计 actor、来源、时间、目标项目、变更摘要和请求 ID。

## 8. Hermes Skill 需求

Skill 应包含：

- 适用场景和禁止场景。
- API 地址、鉴权环境变量和安全规则。
- 动态 Schema 完整说明及示例。
- 新建、查询、查重、更新、归档操作步骤。
- 强制确认规则：没有用户明确确认不得调用写接口。
- 冲突、校验失败、Token 失效和网络失败的处理方式。
- 不得伪造用户确认，不得发送平台不支持的原始 HTML。
- 成功后向用户返回项目名称、变更摘要和网站详情地址。

## 9. 前端需求

### 9.1 工作台

- 左侧主导航，包含工作台、全部项目、待办日程、已归档和系统设置。
- 顶部提供全局搜索、负责人筛选和主要创建操作。
- 概览指标仅展示运营必要信息，不做装饰性图表。
- 项目列表支持状态、负责人、紧急度和更新时间筛选。
- 每个项目卡片的摘要字段来自动态内容中的 `visibility: summary`。

### 9.2 项目详情

- 顶部固定展示系统字段和项目操作。
- 项目详情使用独立页面，不与项目列表并排挤在同一工作区。
- 主体按 Hermes 提交的动态标签页组织，每次只展示当前标签页内容，不把全部信息纵向堆在一页。
- 不同项目可以拥有完全不同的标签名称、数量、顺序和内容类型。
- 每个标签页内部再按动态 section 和 block 渲染。
- 重要与危险内容有统一且可访问的视觉语义。
- 支持标签切换、打印和响应式布局。
- 显示最近同步来源、版本和更新时间。

### 9.3 动态编辑器

- 可增删、移动 section 与 block。
- 根据 block 类型显示匹配的编辑控件。
- 编辑时实时预览，但不允许输入原始 HTML。
- 离开未保存页面时提示。

## 10. 数据迁移

- 现有固定字段映射为“项目概览”“关键节点”“投标准备”等动态 sections。
- 保留项目 ID、用户、审计和归档记录。
- 旧 AI 文件解析与项目问答入口停用，相关历史记录只读保留或按迁移策略清理。
- 迁移脚本必须可重复执行，并输出成功、跳过和失败明细。

## 11. 安全与隐私

- API Token 不出现在页面源码、日志正文或 Skill 文件中。
- 动态文本输出统一转义，URL 使用协议白名单。
- 文件下载必须经过权限检查，不暴露物理存储路径。
- 敏感配置只通过环境变量或受保护的设置存储。
- 登录、Token 调用、项目写入、归档均进入审计日志。

## 12. 验收场景

1. 两个项目包含完全不同的 section 和 block，页面均正确呈现。
2. 未确认的数据不会通过 Hermes Skill 写入正式项目。
3. 重复幂等键不会创建两个项目。
4. 旧版本更新请求返回冲突，不覆盖新数据。
5. 恶意 HTML 和脚本按普通文本显示或被拒绝。
6. 375px、768px、1440px 宽度下无横向溢出和内容遮挡。
7. 键盘可访问所有主要操作，正文对比度满足 WCAG AA。
8. 每次 Hermes 写入均能在审计页查到变更主体和请求 ID。
